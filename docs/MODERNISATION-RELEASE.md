# Side-Quest modernisation release candidate
Combines previously reviewed cleanup #363, Learning Support intake #364, Cloudflare readiness #365 and Parent Hub performance #366. Do not merge those separately if this release is chosen.
No D1 migration or production write. Preserve all family records, membership entitlements, Square Online billing, child/offline routes, Document Studio and historical migration files.
Release gate:
1. Resolve the Cloudflare billing deadline and verify independently stored D1 and R2 backups.
2. Full GitHub CI and visual proofs on this integrated branch. Check Cloudflare build preview isolation; production preview failures are expected for non-main branches, and the guard must remain.
3. On separately authenticated staging, verify Square sandbox subscription activation/renewal/cancellation/undo, document exports, new free Learning Support account and request, Owner HQ private responses, expired-member access, and no child access. No live transactions.
4. Check Cloudflare dashboard AI overrides, account-wide observability usage and spend alerts; sample rate proposal is 10% (not a spending cap).
5. Compare bundle size and real performance on an Australian device, then deploy from main with an explicit rollback point.
6. Do not delete historical tables/records or legacy purchase entitlements. Avoid new paid services until usage is measured.
Limitations: Learning Support is enquiry intake/manual quotations, not paid checkout/automatic bookings. WWCC/safeguarding/insurance and service terms must be confirmed before live tutoring. Future work: background AI generation, query plans/indexes, accessibility and further measured performance improvements.

Student UX: distinguish API failure from genuinely empty work, provide retry and reconnect refresh, flag unavailable calendar dates, accessible week navigation and correct waiting-for-help states. No offline storage, entitlement or lesson format changes. Added retry regression test.

Student dashboard batches legacy lesson reads with a family/shared scope and preserves snapshots and child-safe filtering. Added open legacy assignment privacy regression. No changes to assignment limits or offline cache formats.


AI phase: opt-in scheduled lesson-set writer, existing five-minute cron, no new binding or migration. Off by default (AI_BACKGROUND_BATCHES unset); enable only in isolated staging first. One pending lesson per tick; excludes unconfirmed legacy requests, suspended families, deleted creators, dismissed/paused sets and sets with failed/generating items. Membership and platform budget checks remain. No automatic retry on uncertain failures; retry remains explicit. Pause is prospective, not cancellation of in-flight work. Validate long running requests, cost cap/concurrency, timeout recovery, multiple families, and actual Cloudflare scheduled runtime before enabling production. Single lesson and Auto-Quest generation still use existing interactive workflows; no stage checkpoints yet.


Learning Support proposals: additive migration 0075 (also idempotently ensured on quote routes). Owner proposes scope, delivery details, AUD total and validity; only submitting parent can express interest or decline, including expired preview accounts. Single open immutable proposal, explicit withdrawal before replacement. No contract acceptance, payment, booking or membership change. Owner inbox is marked unread on parent response; parent receives in-app notification on issue. Email delivery of new proposals is not yet implemented. Paid services remain subject to confirmed policies and staging. Backup and apply migration explicitly before production (no destructive SQL).

Quote history is batched into the private Learning Support list response; individual refresh remains available. Migration 0075 supersedes earlier zero-migration release notes.


Standalone Learning Support: migration 0076 creates isolated email links, sessions, requests, messages and quotes; no families/users/trials are created. Single-use hashed links (30 min), hashed guest session tokens (12 h), separate header and sessionStorage, explicit redemption, throttled email requests, owner passkey routes, scoped history and proposal responses. SUPPORT_GUEST_ENABLED must be true to use portal; default off until isolated staging proves email delivery, session security and accessibility. Existing member enquiry path remains. Guest email notices use production SITE_URL: configure and test staging link origin before enabling. No classroom, payment or booking yet. Additive migrations 0075 and 0076 require backups and verification.

Guest rollout gate: public status hides the portal launch button until explicitly enabled and email is configured. Staging requires SUPPORT_GUEST_ORIGIN equal to the isolated side-quest-staging workers.dev origin; never uses request Host to generate links. Production uses canonical SITE_URL. Set flag only after separate test email delivery and production data backup.


Service arrangements and Square sandbox: additive migration 0077. Shared order ledger for member and guest proposals, immutable server-derived AUD price, owner-defined terms, optional UTC appointment interval with atomic overlap prevention, parent confirmation, no-charge completion, sandbox-only hosted checkout (SUPPORT_CHECKOUT_TEST=true with sandbox credentials), stable idempotency, signature-verified/retrieved Square payment isolation from membership. Checkout disabled for live credentials. Unstarted orders only may be cancelled; once checkout is attempted, reconcile in Square before releasing the slot. Refunds observed on completed-payment updates flag review; dedicated refund webhooks, cancellation/refund reconciliation, notifications, availability calendar and classroom are still outstanding. Do not activate paid services before those gaps, policies and staging checks are addressed. No new subscriptions.

Refund.created/updated notifications now re-read the refund from Square and mark matched tutoring orders for manual review. Subscription refund behaviour remains unchanged. Quote withdrawal and order creation are mutually exclusive at the SQL write boundary. Automatic refund initiation, late-payment resolution and safe release of a slot after checkout remain unimplemented; no live checkout.


**Revised payment decision:** manual Square invoices supersede sandbox hosted checkout. Migration 0078 adds invoice references, due dates, issuer and verifier. No Square API charge or invoice creation. Membership billing unchanged. Old sandbox orders/webhooks preserved for reconciliation; checkout route returns 410. Overdue bookings held until owner checks nonpayment and cancels invoice in Square. Paid-order refund reconciliation and classroom access outstanding. Test both channels and email before release.


Classroom pilot and central calendar: migration 0079. Owner-only calendar combines paid and provisional appointments and overdue invoices across both customer channels. Shared teaching board (owner notes, parent/tutor drawing, bounded payload, revision conflict handling, owner open/close). Appointment must be paid or free, no legacy checkout, access checked on each call, 10 min before to 10 min after, guardian-supervised, no private child login. SUPPORT_CLASSROOM_ENABLED off by default. Polls every 4 seconds only while mounted and visible; benchmark D1 request costs and Owner HQ step-up expiry, improve collaboration/retention/accessibility before production. No video/audio/screen sharing or resource upload yet; no new paid service. Confirm safeguarding and retention policy before enabling.


Video foundation (0080): Cloudflare RealtimeKit server adapter, staging-only even with flags set. Owner creates at most one room per appointment, no automatic creation retry after uncertain provider responses. Tutor and family roles use distinct approved presets; credentials stay server-side, tokens use appointment expiry and never persist in D1. Explicit closure deactivates provider meeting and kicks participants; maintenance attempts overdue/closed/unpaid-room cleanup every five minutes, including flag-off. Provider failures need dashboard reconciliation. Browser SDK NOT installed yet: pin and review dependencies and lockfile before mounting video; validate permission presets (no recording, chat, file exchange, AI, livestream, unrelated invitations), token refresh/revocation, actual close behavior, inactive-session responses, provider billing and privacy. No real API calls or resource provision. See official API https://developers.cloudflare.com/api/resources/realtime_kit/ and https://developers.cloudflare.com/realtime/realtimekit/platform/pricing/. Do not enable production before actual two-device tests and safeguarding review.


Browser video pilot: pinned RealtimeKit Web Core 2.1.0 (official release 16 Nov 2026). Uses custom Side-Quest video tiles, explicit guardian consent, media off by default, tutor-only screen sharing UI, separate leave-video and leave-workspace controls, unmount/room closure cleanup, no external CDN script. `node frontend/scripts/prepare-realtimekit-pilot.mjs` is an explicit isolated staging preparation step that fetches the exact npm tarball without lifecycle scripts, checks registry-reported integrity, extracts only browser.js, and records a SHA-256 manifest. Do NOT run for production. Registry inaccessible from current development container; package retrieval, manifest review, SDK global, licence, real two-device media, permission presets and provider termination still unverified. Staging-only server gate remains. Owner HQ passkey step-up currently expires after 15 minutes; test reauth during longer sessions; do not weaken global Owner HQ controls. SDK polling is local browser state; board remains independently usable. Source: https://developers.cloudflare.com/realtime/realtimekit/humans/core/ and https://developers.cloudflare.com/realtime/realtimekit/release-notes/web-core/.


Tutor resource studio (0081): private searchable, editable, duplicable decks for subject/year/topic; each slide separates learner-facing material from private tutor explanations and answers. Owner review required before presentation; revision check blocks stale deck edits/presentation. Classroom snapshots only current learner-facing slide, never notes or unpublished slides. AI-assisted generic topic drafts use existing Workers AI, disabled unless SUPPORT_RESOURCE_AI=true; bounded single inference with existing cost cap and per-owner 5/hour throttle, never automatically saved/reviewed. No new subscription. This is native presentation-style content, not PPTX import/export. AI accuracy review, presentation accessibility and real classroom testing remain required. Private PDF upload/delivery and session summaries not yet implemented.


Quote-linked learning plans (0082): optional reviewed 1–4 lesson sequence with parent-facing objectives, activities, progress checks, follow-up practice and private detailed tutor guides/answers. Atomic quote issuance and immutable plan snapshot, no draft auto-send; both member and guest scoped read routes, owner-only private notes. AI drafts use same opt-in flag, shared owner throttle and platform limits as slide drafts, only explicit de-identified input, no automatic AI invocation on a customer enquiry. A multi-lesson proposal is a plan only: current order model supports one live appointment per accepted quote, so recurring/multiple bookings and per-lesson delivery still require implementation. No automatic pricing or guarantee of attainment. Review and staging required.


Outage continuity: confirmed orders have an owner-only backup preview and explicit email action. Parent-facing plan/arrangements are downloadable and can be emailed ahead as plain text, with a distinct private tutor pack. Optional unique Google Meet URL is allowlisted and requires recorded-in-request owner attestations of guardian agreement, host admission/restricted access and no recording. Never auto-join or auto-create a meeting. Parent can save their proposal plan independently. In a total Cloudflare outage use previously downloaded packs and existing verified email/Square correspondence; if the backup provider is also unavailable, arrange no-extra-charge completion/reschedule or appropriate refund. This is procedural failover, not automated multi-region recovery; actual email delivery, host controls and independently accessible contact route need testing. Private tutor downloads must be secured; do not send to customers. Existing backups of D1/R2 still required. No new subscriptions or real emails sent during development.

TypeScript correction: explicitly handle absent route params on dynamic Hono paths and type drawing coordinates. AI resource requests have a separate 15/day per-owner throttle as well as the shared hourly throttle and existing platform check. The platform ai_usage ledger does not count resource drafts themselves; the inference cost ledger records model invocations. Member backup email may predate mandatory verification; owner must check recipient against established parent correspondence before sending.

Guided intake: shared form for standalone and member parents captures the difficulty, strengths, special interests, learning preferences, desired outcomes and optional availability. Server validates each optional field and keeps combined text within legacy feedback limits. Durable request saved before notification. Owner notification includes request reference and private inbox link, not learner details; requires OWNER_NOTIFICATION_EMAIL and working EMAIL binding. No AI/quote/booking/payment automatically triggered. Email delivery must be verified in staging.

External materials (0083): owner-only R2 library under support-private/ with separate metadata and order-specific grants. PDF, PNG, JPEG up to 5 MB; signature/extension checks are not malware scanning, accept only trusted owner-reviewed files. Explicit learner-copy permission; tutor files cannot be granted. Parents download scoped resources after confirmed payment or completion; archive/revoke prevents future downloads only. No public links, no raw Office upload, no embedded PDF presentation yet: export Office to PDF, download before class and share the window in the video pilot. Actual R2 storage, file safety, privacy and access require staging checks. Retention/purge and upload storage budget remain to be finalized. No new paid services provisioned.

Presentation exchange and classroom visuals: native JSON v1 import/export with downloadable example; imports strip identifiers, status and approval and enter the editor as a draft. No PowerPoint binary parsing or Office conversion on server. Reviewed learner PNG/JPEG displayed in the classroom through an authenticated, current-slide-only endpoint with no ongoing download grant. Browser object URLs released on change/unmount; image alt text currently uses title. External PDFs remain downloaded or shared via video; direct PDF rendering/annotation, native PPTX import, multi-page image deck grouping and accessibility testing outstanding. No migration needed.

Tutor diary (0084): owner-only per-order learner nickname, subject/year, goals, interests/adjustments, teaching approach, timed activities, materials, preparation, follow-up and reflection, with readiness and revision protection. Approved proposal lesson can prefill preparation (review and edit). Daily/7-day Sydney calendar combines bookings and personal unavailable blocks; preparation/wrap-up buffers configurable at order creation, default UI 10 min each, legacy API default 0. Atomic order/diary batch checks both buffers and blocked times, and block creation checks reservations. No new fees or parent data exposure. Separate learner enquiries remain necessary for siblings; no cross-request learner profile or multi-appointment package yet. Buffers cannot be edited after booking; rescheduling workflow still outstanding. Private offline sheets contain learner labels and notes; store securely. Test DST, real scheduling and browser workflows before enabling.

Parent time invitations (0085): owner selects up to 12 candidate starts for a proposal, common duration, buffers and terms; sends a private portal notification. Parent sees only conflict-filtered options grouped by Sydney date. Interest is required before selection; selection uses server-stored terms and price, atomically checks current offer identity and availability against both customer channels and busy blocks, creates awaiting_confirmation order, and notifies owner. Parent must then confirm arrangements; Square invoice and owner payment confirmation still separate. Offered options are not reserved until selected; replacing/withdrawing invalidates old options without changing existing bookings. Actual email, DST, both guest/member browser paths and concurrent selection need staging testing. No automatic scheduling, public calendar, or additional fees.
